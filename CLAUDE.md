# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A single Google Apps Script file (`TournoiBaseball_Script.gs`) that turns a Google Sheet into a full tournament management system for a 13U baseball tournament (Baseball Québec). There is no build system, package manager, or test framework — this is a `.gs` file meant to be pasted whole into the Apps Script editor bound to a Google Sheet.

Supporting files (not code, read for domain context when relevant):
- `Regles13U_2026.md` / `ReglesRegie2026.pdf` — official Baseball Québec rules (field dimensions, game length, mercy rule, extra innings, **Art. 42.11 tiebreaker procedure**). The tiebreaker logic in the script is a direct implementation of Art. 42.11.
- `Horaire-tournoi-2026.xlsx` — the tournament's own schedule file, produced each year by the ABMR tournament committee (NOT an official Baseball Québec file — only the rules above are). Its `Horaire globalArbitre` tab defines the exact column format that gets pasted into the "Configuration" sheet (`# de match`, `# pool`, `Jour`, `Heure`, `Terrain`, `Équipe 1`, `Équipe 2`, plus referee/scorekeeper columns that the script ignores).
- `Équipes.txt` — scratch notes, not authoritative.

## Working with the code

There is no build/lint/test command. The only practical verification available offline is a syntax check:

```bash
cp TournoiBaseball_Script.gs /tmp/check.js && node --check /tmp/check.js
```

This catches JS syntax errors only — it does not validate Apps Script globals (`SpreadsheetApp`, `Logger`, etc.), since `node --check` parses without executing. There is no way to actually run the script outside the Apps Script runtime; real verification happens by pasting into a bound script and exercising the custom menu.

There is also an offline test of the tiebreaker logic (Art. 42.11), which is the most intricate and fragile part of the file:

```bash
node tests/test_tiebreaker.js
```

It `eval`s the real functions out of `TournoiBaseball_Script.gs` (the pure standings functions that never touch `SpreadsheetApp`) and runs them on a hand-built 3-way circular-tie scenario, asserting that a score change which leaves the V-D records identical still flips the pool order via the RA/DefInn ratio (Priority 2). It exits non-zero on failure. Like `node --check`, this only covers pure logic — it does NOT exercise the Apps Script integration (sheet I/O, the live-recalc trigger `handleResultEdit`); that still requires pasting into a bound sheet and editing a score.

**Deploying a change:** paste the entire file into Extensions > Apps Script > Code.gs in the target Google Sheet, save, reload the spreadsheet, then run "Initialiser les feuilles" from the "🏆 Tournoi Baseball" menu to rebuild sheet structure (this clears and regenerates every sheet — it does not preserve scores already entered in Résultats). A second menu item, "Initialiser (conserver Configuration)" (`createAllSheetsKeepConfig`), does the same rebuild but leaves the `Configuration` sheet untouched if it exists, so the pasted schedule survives a code-redeploy (Résultats are still rebuilt → scores cleared; re-run "Générer les matchs"). Both delegate to `rebuildSheets(keepConfig)`. **Destructive menu items guard against an accidental mid-tournament click with a `ui.alert(...YES_NO)` confirmation** (`ui.Button.YES` gate, early `return` otherwise): "Initialiser les feuilles" (`createAllSheets`) asks **twice** (it wipes the pasted schedule *and* every score — irreversible), "Initialiser (conserver Configuration)" (`createAllSheetsKeepConfig`) and "Générer les matchs" (`generateGames`) ask once, and "Effacer les résultats" (`clearResults`) / "🧪 Simuler résultats de match" (`simulateMatchResults`) already had their own. The prompts live in the **menu-wrapper functions**, not in `rebuildSheets`/`readScheduleRows`, so the underlying rebuild/generate logic stays callable without a UI prompt. The remaining menu items are non-destructive (they only rebuild *derived/calculated* sheets or are read-only) and deliberately have no prompt: "Mettre à jour les classements" (`calculateStandings` — recompute only; P-T calculated cols + rebuilt `Classements`/`Grand livre`, with the "Forcer 2e"/"Forcer rang" admin overrides read back before the clear so nothing is lost), "📒 Grand livre" (`buildLedgerSheet`), "⚡ Activer la mise à jour auto" (`installTriggers`, idempotent), "📦 Exporter ZIP" (`exportSheetsToZip`, creates a Drive file), "📱 Lien affichage public" (`showPublicUrl`, read-only). **Also run "⚡ Activer la mise à jour auto" once after each code paste** — the live-recalc trigger is an *installable* trigger (`handleResultEdit`), not a simple one, so it must be (re)registered by the owner via `installTriggers()`; pasting code alone does not arm it.

**Public display web app (Facebook):** the script also publishes a read-only web page (`doGet`) for the communications volunteers to screenshot/share the standings on the tournament's Facebook page from their phones. It is a **separate deployment** from pasting code: in the Apps Script editor, *Déployer → Nouveau déploiement → Application Web*, "Exécuter en tant que" = me (owner, to read the sheets), "Qui a accès" = anyone with the link — **re-deploy a new version after every change to the web-app code** (pasting alone does not update the live `/exec` URL). The menu item "📱 Lien affichage public" (`showPublicUrl`) shows the deployed URL. The page reuses the **same standings engine** as the sheets via `computeStandingsModel(ss, classe)` — a read-only, sheet-free function that replays `buildStandingsSheet`'s exact calc sequence (same pure functions + admin overrides) so the public view can never diverge from the `Classements` tabs. Rendering is a single self-contained HTML/CSS/JS template string (`PUBLIC_HTML_TEMPLATE_`, injected via `renderPublicHtml_`, data embedded as JSON with `<` escaped to prevent `</script>` breakout); the page is deliberately stripped of all admin (Avancement/Forcer 2e/Notes/Critère décisif/tiebreak tables) — only Rang/Équipe/V-D/RD + semifinal qualifiers + `ℹ` banners — with a class A/B and pool 1/2/3/Tout selector. The page does **not** auto-reload (an earlier 60 s `setInterval(location.reload)` was removed at the maintainer's request — the Facebook volunteers reload manually); the footer says "Rechargez la page pour voir les derniers résultats."

**Semifinal seeding (positions 1-2-3-4) is hidden until every pool game of the class is played.** The positions 1/2/3 (pool winners ordered by Étape C) and position 4 (best 2nd, Étape B) form an *inter-pool* ranking that is only reliable once all pool games are in — before that the best-2nd and the order of the firsts shift with each score entered, which would mislead the Facebook volunteers screenshotting a provisional standings. So `poolPlayCompletion(classe)` (near `getMatchRows`; counts `getMatchRows(classe)` rows and their `played` flag → `{total, played, complete}`, `complete = total>0 && played===total`) gates the reveal **per class independently** (class A can reveal while class B is still incomplete). While incomplete: `buildStandingsSheet` passes an **empty `seedByTeam`** to `writePoolSection` (so the "Avancement" column stays blank) and replaces Sections 4/5 + the DEMI-FINALES summary with `writeSeedingPendingBanner` (a progress banner "Parties jouées : played/total"); `computeStandingsModel` nulls every `seed` (pool rows + `secondsCard`) and returns `poolsComplete`/`poolPlayed`/`poolTotal`, and the public template's `appendSemifinalBlock` shows the same waiting note instead of the "Meilleur 2e"/"Demi-finales" cards (the pool cards' "Rang" column is then blank automatically since seeds are null). The **per-pool internal standings** (rank, 1er/2e highlight, V-D, RD, intra-pool tiebreak tables, "Forcer 2e") keep showing live throughout — only the inter-pool block waits. It flips on automatically via the live recalc when the last pool score is entered. The Étape B/C "Forcer rang" (P4) input cells only exist once the sections render (i.e. once complete), which is harmless since inter-pool P4 is only relevant then.

**Git workflow:** commit changes, but **do NOT `git push`** — the maintainer handles all pushes themselves. Stop after `git commit`.

## Architecture

The script is organized as sections (search for `// ====` banners) in this order: constants → menu → sheet creation → match generation → data reading → inning-fraction math → standings calculation → standings sheet rendering → clear results → simulation → utilities → public display web app (`doGet`). The data flow across these sections is the key thing to understand before editing:

```
Configuration (pasted schedule)
   → readScheduleRows() / parsePoolClasse()   [parses "# pool" like "3A" into {pool:3, classe:'A'}]
   → generateGames()                          [routes each match into Résultats A or B]
   → Résultats A / Résultats B                [registrar fills in scores + Équipe Locale]
   → getGameResults() + calculateInnings()    [computes winner + fractional innings]
   → calculateStandings() → buildStandingsSheet()  [pool standings, Étape B/C, semifinals]
```

**Configuration is a pasted schedule, not a roster.** It mirrors the exact column layout of the `Horaire globalArbitre` tab from the ABMR tournament's Excel file (`createConfigSheet`). There's no per-team input UI — the registrar copy-pastes the year's real schedule starting at A2 every year, and everything else regenerates from it. `getTeams(classe)` derives the team roster per pool by scanning this schedule (teams are no longer declared anywhere separately).

**Home team is unknown at generation time and is a separate concept from "Équipe 1"/"Équipe 2".** The schedule only pairs two teams; nobody knows who's the home team until the game is actually played. `generateGames()` writes "Équipe 1"/"Équipe 2" (just the matchup, no home/away meaning) plus an empty "Équipe Locale" column with a per-row dropdown (only the 2 teams in that match). The registrar sets it when entering the score. `getGameResults()` resolves it: if "Équipe Locale" matches Équipe 1 or 2 it's used directly (`homeKnown = true`); if blank, the code falls back to a symmetric (no home-win advantage) inning calculation and logs a warning (`homeKnown = false`). **This now matters for *any* home win, not just early-ended games:** since a home win always means the home team didn't complete its last at-bat (walk-off, or already leading and not batting the bottom of the last inning — see the inning-fractions section), even a full-regulation home win is asymmetric (5/6/6/5, not 6/6/6/6). Leaving "Équipe Locale" blank on a home win therefore loses that half/full inning of precision. Only a *visitor* win is genuinely symmetric regardless of who's home.

**Inning fractions are the trickiest math in the file** (`calculateInnings`). Tiebreaker ratios (RA/DefInn, RS/OffInn) need the *real* number of innings each side played, not just the inning count of the game. **Any home win** means the home team's last at-bat was not completed: either a walk-off (winning run before 3 outs) or the home team was already ahead after the top of the last inning and never batted the bottom. Both collapse to the same formula — home off = `(K-1) + L/3`, visitor def = the same fraction — so `localeWinsBottom` is simply `homeKnown && scoreLocal > scoreVisiteur` (no inning-count gate). Consequence: a full-regulation home win is 5/6/6/5, **not** symmetric; only a visitor win (or `homeKnown=false`) yields 6/6/6/6. **Regulation length is per-game, via the "Manches prévues" column** (manual col M, default 6, distinct from col K "Manches complètes" = last inning actually reached): `getGameResults` reads it and passes it to `calculateInnings(...)` as the `regulation` argument, which credits the **winner of a Mercy/Forfait** with `regulation` defensive innings (5 on a rain-shortened day, not a hardcoded 6). This is also explained to end users via column header notes (`setNote()` on header cells in `createResultsSheet`) and the auto-generated "Aide" sheet (`createHelpSheet`) — if you change the math, update both, since they're meant to be self-contained (no cross-referencing required while a registrar is entering scores). **Known limitation (future work):** a Mercy *won by the visitor* where the losing home team didn't bat the bottom of the last inning still credits the home team's offense at N (not N−1); not yet corrected — revisit if a real case requires it.

**Forfait scoring is fully synthetic (Art. 42.11).** For a `'Forfait'` the registrar only *designates the winner* by giving it a higher raw score (the exact numbers are ignored); `getGameResults` then overwrites the score to `manchesPrevues`–`0` (1 run per regulation inning to the winner, 0 to the loser) before anything downstream reads it, so PP/PC and the V-D record reflect that official score. `calculateInnings` credits the **winner** with `0` offensive innings and `regulation` defensive innings, and the **loser** with `regulation` offensive innings and `0` defensive — asymmetric, and **inverted from the old behavior** (which gave the winner regulation/regulation and the loser 0/0). Because the winner has 0 offensive innings (RS ratio degenerate) and the loser 0 defensive (RA ratio degenerate), forfaits would distort the ratios — which is exactly why **Note 5** excludes them from the Meilleur-deuxième ratios (see the standings section).

**Tiebreaker resolution is recursive and three-tiered**, mirroring Art. 42.11 exactly:
- Step A (`useAllGames=false`): rank within a pool using head-to-head games only among tied teams.
- Steps B/C (`useAllGames=true`): rank pool winners (Étape C, positions 1-3) and pool runners-up (Étape B, position 4 / best 2nd) using each team's full set of pool games, since they never played each other directly.
- **Step A is two-level (`orderTeams`).** For `useAllGames=false` (Step A), `orderTeams()` first groups the pool by each team's *overall* pool V-D record (via `groupByMetric`) — that's what determines *who is tied* and the order **between** groups — then, for each tied group of ≥2, calls `tiebreaker(group, games, false)`, which sets the scope to `headToHeadGames(group)` (games played **strictly between those tied teams**) and runs the priorities on it. The scope is narrowed **only at this first split**; inside a tied group the Note 2 recursion keeps that group's head-to-head scope. For B/C (`useAllGames=true`) `orderTeams` skips the grouping and calls `tiebreaker` once over all involving games (the teams never played each other). `tiebreaker()` fixes the relevant-games scope for the pass (head-to-head **of the tied group** for Step A, all involving games for B/C), then `applyPriorities()` walks the priorities in order (head-to-head record → RA/DefInn ratio → RS/OffInn ratio → "innings ahead", which isn't automated and is flagged with `__needsManualCheck` for the registrar to resolve via the **"Forcer rang" override column** — see the Priority-4 override paragraph below). **Note 2 (partial resolution):** when a priority only partially separates a tie, each still-tied subgroup *continues to the next priority* (not back to Priority 1) computed on the *original group's* games (the fixed scope), **not** re-restricted to the subgroup. This mirrors the official QC/RS/CN example in the PDF (`QC > CN > RS`), where Priority 2 isolates QC and the {RS,CN} remainder must be settled by Priority 3 on the full 3-team scope — restarting at Priority 1 (head-to-head) would wrongly put RS ahead. **Where it stops:** once a subgroup exhausts the automatable ratios (Priority 2 then 3) without separating, the next priority is **Priority 4 ("manches avec l'avance au pointage" / innings-with-the-lead)**, which the script *cannot* compute — it needs the per-inning scoresheet it doesn't have. The registrar computes it by hand on the paper scoresheets and enters the resulting order in the **"Forcer rang" column** of the bris d'égalité table; the engine applies that via `resolveForcedRanks` (see the Priority-4 override paragraph). Until a valid order is entered, the subgroup keeps a provisional alphabetical order and `__needsManualCheck` stays raised. The "go back to Priority 1" clause of Note 2 only applies *after* Priority 4, so it is never reached automatically. **The `writeTiebreakTable` display shares this exact per-group head-to-head scope** (it regroups `orderedNames` by overall record, then recomputes each tied team's stats on `headToHeadGames(group)` for Step A), so the bris d'égalité table shows the *restricted* record — e.g. `1-0`/`0-1` for a two-team tie, **not** the pool's `2-1` — and `decisiveCriterion` now reports a Priority-1 `Fiche x-y > a-b` when the head-to-head separates the pair (before falling through to the RD/RO/`Manuel (P4)` branches). (Two earlier bugs, both fixed: Priority 4 once jumped straight back to Priority 1 re-restricted to the pair's head-to-head; and — the more serious one — Step A passed the *whole pool* to `tiebreaker` as a single tied group, so Priority 1 collapsed into the overall record and P2/P3 ran over **all** pool games. The head-to-head winner of a two-team sub-tie could then be ranked **below** the loser, and the "tête-à-tête" table showed full-pool `2-1` records. The two-level `orderTeams` above is the fix; `tests/test_tiebreaker.js` locks it in with the "Étape A = parties entre équipes à égalité" regression.)

**Note 4 (extra innings) is now AUTO-computed from one extra input.** Art. 42.11 Note 4 requires that runs scored/allowed in *extra* innings be excluded from the RA/RS ratios. The key insight that makes this automatable from a single number: a game only goes to extra innings if it's *tied* at the end of regulation (Art. 42.4), so the regulation score is always `X–X` — both teams scored the same regulation total `X`. The registrar therefore enters just that one number in the **"Pointage régl. (suppl.)" column (manual col O)**, filled only when Type de fin = `'Supplémentaires'`. `getGameResults` reads it (`suppTieRaw`) and, for a supp game with a valid tie score, builds **regulation-only ratio fields** on the game object: `regRsLocal = regRsVisiteur = X` and `regOffLocal = regDefLocal = regOffVisiteur = regDefVisiteur = manchesPrevues` (col M) — i.e. the supp game contributes a *neutral* `X/X` over `M/M` to each team's ratio, with the extra-inning runs excluded. For every non-supp game these `reg*` fields just equal the real score/innings, so nothing changes. `computeTeamStats` keeps **two parallel families of accumulators**: the *regulation* basis — `rsNum`/`raNum` (regulation runs) and `offInn`/`defInn` (regulation innings) → ratios `rsRatio`/`raRatio` — used by the **tiebreaker engine** and the **bris d'égalité tables**; and the *real* basis — `rs`/`ra` (full real runs, displayed PP/PC) and `offInnFull`/`defInnFull` (real innings, suppl. included) → ratios `rsRatioFull`/`raRatioFull` — used by the **pool standings table**. It uses a `val(x, fallback)` helper so hand-built game objects (the offline test) without `reg*` fields fall back to the full values (the `*Full` accumulators read `g.offLocal`/`g.defLocal` directly, which always exist). **Note 5 (forfaits excluded from the Meilleur deuxième):** `computeTeamStats` takes a third arg `excludeForfaitRatios`; when true it skips a `'Forfait'` game's **entire** ratio contribution — both the runs (`rsNum`/`raNum`) and the innings (`offInn`/`defInn`) — so the ratio is genuinely dropped, not left with a numerator and no denominator. The tiebreaker (`applyPriorities`) and the bris tables/`writeAdvancementSection` pass `useAllGames` as this flag, so forfaits are excluded from the ratios in Steps B/C (the Meilleur-deuxième / pool-winner ranking) but kept in Step A and the pool table (`excludeForfaitRatios=false`). The V-D record and the real `rs`/`ra` (PP/PC) are accumulated outside this gate, so they always count. **Display decision (revised — Note 4 is tiebreaker-only):** the **pool table** (`writePoolSection`) shows *real* MO/MD/RD/RO over all innings played (suppl. included), so RD = PC÷MD lands exactly there (notes via `rdCalcNoteFull`/`roCalcNoteFull`). The Note-4 exclusion of extra innings applies **only in the bris d'égalité tables** (`writeTiebreakTable`, Step A/B/C), which is where ties are actually broken — those show the *regulation* PP/PC/MO/MD/RD/RO (PP=`rsNum`, PC=`raNum`), so RD=PC÷MD lands there too, on the regulation basis (notes via `rdCalcNote`/`roCalcNote`). Consequence: for a supp game the same team's RD/RO (and PP/PC/MO/MD) **differ between the pool table and the bris table** — intended, and the bris table's `ℹ` "Manches supplémentaires exclues" banner explains it. (`writeAdvancementSection`, the Étape B/C ranking, keeps the regulation `raRatio`/`rsRatio` — it *is* a tiebreaker ranking.) Earlier this was "Option A transparent" (regulation-only everywhere, so pool-table RD≠PC÷MD on a supp game); the maintainer reversed it because Note 4 is literally a sub-rule of the tiebreaker article (Art. 42.11) and the pool table's ratios are an app-level info display, not dictated by the rules. `writePoolSection` shows an `ℹ` "Note 4 appliquée" banner for resolved supp games and a `⚠` "Pointage régl. manquant" banner if a supp game's col O is blank (`g.suppNeedsTie`, set in `getGameResults`; that game falls back to no-exclusion until filled). `writeAdvancementSection` mirrors this in the Étape B/C `Note` column. `isRowComplete` now requires col O for a `'Supplémentaires'` row (so live recalc waits for it); `gameIsSupp(g)` still just detects the type. **Known edge (time-expiry tie):** if a game is tied by time before reaching M innings and then plays an "open" inning, the regulation innings aren't M — the registrar handles this by setting col M (Manches prévues) to the actual regular-inning count for that game.

**Result sheet columns are positional, not named lookups** — every function that reads/writes `Résultats A/B` (`createResultsSheet`, `generateGames`, `getGameResults`, `writeCalculatedResults` / `writeRowCalc`, `clearResults`, `simulateMatchResults`, `handleResultEdit`) hardcodes column numbers (currently **20 columns**: A-G auto-copied from Configuration, **H-O manual entry** — H/I scores, J Équipe Locale, K Manches complètes, L Retraits en fin, **M Manches prévues** (regulation length, default 6), N Type de fin, **O Pointage régl. (suppl.)** (the regulation tie score X, blank except on `'Supplémentaires'` games — drives Note 4) — and **P-T calculated** (P Gagnant, Q-T MO/MD Éq.1 & Éq.2)). There's no named-range or header-lookup abstraction, so changing the column layout means updating every one of those functions' column indices in lockstep — there is no single source of truth for "column J is Équipe Locale" beyond the header string itself. `writeRowCalc(sheet, rowIndex, game)` is the one place that writes the P-T calculated block for a single row; both `writeCalculatedResults` (full-sheet loop) and `handleResultEdit` (targeted single-row) go through it. Note the P-T block writes the *actual* innings played (suppl. included), not the Note-4 regulation innings — the latter live only in the in-memory `reg*` fields used by `computeTeamStats`. **Q-T are indexed by Équipe 1/Équipe 2 (schedule position, cols F/G), NOT by local/visiteuse.** The `game` object reasons in home/away (`offLocal`/`defLocal`/`offVisiteur`/`defVisiteur`, local = home team), but the Q-T headers are `MO/MD Éq.1` (= `teamA`, col F) and `MO/MD Éq.2` (= `teamB`, col G) — a fixed matchup position, independent of who ended up home. So `writeRowCalc` must remap via `game.localIsEq1` (`= (local === teamA)`, set in `getGameResults`) before writing: Éq.1 gets the local values only when the home team *is* Équipe 1, otherwise the visitor values, and vice-versa for Éq.2. Writing `offLocal → Q` directly (the pre-fix behavior) silently swapped Q/R with S/T whenever the home team was Équipe 2 (e.g. real game #18: Équipe 2 = home, walk-off, so Q showed the home team's partial-inning offense under the "Éq.1" header). This is **display-only** — the standings engine (`computeTeamStats`, `buildStandingsSheet`) reads the in-memory `game` objects by **team name** (`g.local === team`, `g.offLocal`…) and never reads the Q-T cells, so standings/ratios/public page were always correct; only the Résultats Q-T columns were wrong. It went unnoticed because `simulateMatchResults` always makes Équipe 1 the home team (the accidentally-correct case), and no code path ever *reads back* Q-T (`getGameResults` and `generateGames` read the 20-col width but consume only A-O and discard P-T; `getMatchRows`/public read only A-O).

**Standings recalc runs both on-demand (menu) and live (installable edit trigger).** The menu item "Mettre à jour les classements" → `calculateStandings()` is the authoritative full refresh (rewrites all P-T + rebuilds both standings sheets). On top of that, `handleResultEdit(e)` recalculates live during a real tournament where 2-3 registrars enter scores in parallel while others watch the `Classements` tabs. **It is wired as an *installable* edit trigger, deliberately NOT named `onEdit`:** a simple `onEdit` trigger runs in a restricted auth mode where `LockService` can fail (which would break the multi-user lock), so `installTriggers()` (menu "⚡ Activer la mise à jour auto") registers it instead — it then runs with the owner's authorization while still firing for every collaborator's edits. The owner must run this once after each code paste; pasting code alone does not arm it. The handler is deliberately conservative: it only fires when an edit lands in the manual-entry columns (H-O) of a `Résultats` sheet **and** `isRowComplete()` says the game's row is fully filled — scores H/I, Équipe Locale J, Manches complètes K, Retraits L, and Type N for a normal game (Manches K is required, not defaulted, because rain can shorten a "normal" game to e.g. 5 innings; Manches prévues M is *not* required since it defaults to 6 and is pre-filled), or just the two scores + Type for a `Forfait`, or those plus the Pointage régl. O for a `'Supplémentaires'` game. `isRowComplete` tests *emptiness* (`x !== ''`), never falsiness, so a score/outs value of `0` counts as filled. The whole recalc is wrapped in `LockService.getDocumentLock()` (document lock, **not** user lock — the contention is between different users) acquired defensively (if `LockService` is unavailable it recalcs without the lock rather than throwing) so two stations can never rebuild a `Classements` sheet concurrently and show a half-built standings to watchers. The handler writes only the edited row's P-T (via `writeRowCalc`) plus the `Classements` sheet — never the whole `Résultats` sheet, to avoid disturbing another station's typing. (It also has a second entry path: an edit to **column 13** ("Forcer 2e", admin) **or column 24** ("Forcer rang", Priority-4 manual order) **of a `Classements` sheet** routes to `recalcStandingsOnly`, which rebuilds only that class's standings; see the admin-override and Priority-4 override paragraphs below.) Known gap (covered by the menu fallback): a *bulk* clear of cells won't auto-recalc; only a single-cell score clear (detected via `e.oldValue`) is caught. `buildStandingsSheet` recomputes purely from the in-memory `games` array and never reads the P-T columns, which is what makes the targeted/standings-only path correct.

**Admin override for the Meilleur-deuxième representative (Note 5, forfaits).** Because re-deriving each pool's 2nd-place team with forfeit games removed (the literal Note 5 reading) was judged too risky/complex for a rare case, the maintainer chose a manual lever instead: the admin ticks a **checkbox in column 13 ("Forcer 2e")** of a pool section in the `Classements` sheet, next to the team that should represent that pool in **"SECTION 5 — MEILLEUR 2e (Étape B)"** (checkbox so it toggles off in one click; `readSecondOverrides` also accepts a legacy literal `2` for back-compat). `buildStandingsSheet` calls `resolveSecondRepresentative(standings, markedTeams)` per pool — a **pure, offline-tested** function: it returns the marked team (`forced:true`) if exactly one valid non-rank-1 mark exists, falls back to the rank-2 team otherwise, and **ignores a mark on the rank-1 team** (already qualified via Étape C) or an ambiguous multi-mark, surfacing a `warning`. The resolved team (not necessarily rank-2) is what gets pushed into `seconds` → flows through Étape B and the semifinal summary automatically. **Persistence despite the full `sheet.clear()` rebuild:** `buildStandingsSheet` calls `readSecondOverrides(sheet)` to read the existing ticked checkboxes (keyed by **team name**, stable during a tournament) *before* clearing, then `writePoolSection` re-inserts the checkboxes (`insertCheckboxes()`) and re-ticks the forced team in column 13 — so the admin's input survives every live recalc. (The earlier invariant "`buildStandingsSheet` never reads the P-T columns" still holds; it now reads only column 13 of the prior render.) The override is picked up live: `handleResultEdit` also fires for edits to **column 13 of a `Classements` sheet** (the installable trigger is registered `.forSpreadsheet(ss)`, so it sees every tab) and routes them to `recalcStandingsOnly(e, classe)` — a lock-guarded rebuild of just that class's standings sheet (no `Résultats` P-T writes). Failing that (auto-update not armed), the menu "Mettre à jour les classements" applies it. A `ℹ`/`⚠` banner under the pool section reports the forced 2nd or the ignored mark; additionally, the forced team's row in **Section 5 (Étape B)** carries a `🔒 2e forcé par le registraire` marker in its `Note` column. The `forced` flag rides along on each `seconds` entry (`{team, pool, forced}`), which is exactly the `poolInfo` array `writeAdvancementSection` already receives, so no extra parameter is needed — Étape C's `firsts` entries have no `forced` field, so Section 4 never shows the marker. Only the *candidate selection* is manual — ratios, the Note-5 ratio exclusion, and Étapes A/C are unchanged.

**Registrar override for Priority 4 (the "Forcer rang" column).** Priority 4 ("manches avec l'avance au pointage") is the one tiebreaker criterion the script cannot compute — it needs the per-inning paper scoresheet. (An earlier `Manches_Détail` sheet held per-inning scores for this but was never read by the code and has been removed; redeploying deletes any leftover tab.) Instead, when the engine reaches P4 it leaves a provisional alphabetical order + `__needsManualCheck`, and the registrar — having computed the order by hand on the paper scoresheets — types it into a **"Forcer rang" column (col 24)** added to each bris d'égalité table by `writeTiebreakTable`, on the rows the table marks `⚠ Manuel (P4)`. `resolveForcedRanks(teams, forced)` (a **pure, offline-tested** function shared between the engine and the render) orders the still-tied subgroup by the entered numbers — **relative order only** ("1,3" ≡ "1,2") — and reports `resolved=true` iff no number is duplicated and **at most one** team is left blank; when resolved it clears `__needsManualCheck` and the table's criterion flips to `🔒 Forcé (P4)`. **Precedence is P4-only:** `forced` is threaded `orderTeams → tiebreaker → applyPriorities` and consulted *only* in the P4 branch, so a number typed on a team already separated by P1/P2/P3 is ignored — the override can never contradict a rules-based ratio. Because P4 can hit the **rank-1** slot of a pool, the override also changes who is "1er"/"2e" (Étapes C/B) automatically via `calculatePoolStandings`. **Scoping & persistence:** a team can appear in two bris tables (its pool's Step A *and* an Étape B/C table), so `readForcedRanks(sheet)` (called before `sheet.clear()`, like `readSecondOverrides`) keys entries by **scope** — derived from the col-A section titles aligned row-for-row with the bris block: `"A"+pool` / `"C"` / `"B"` — then by team name; `buildStandingsSheet` passes `forcedRanks["A"+p]` / `["C"]` / `["B"]` to the right call and re-fills the yellow input cells, so the registrar's order survives every live recalc. Picked up live the same way as "Forcer 2e": `handleResultEdit` also fires on col-24 edits of a `Classements` sheet → `recalcStandingsOnly`. The Étape B/C `Note` column shows `⚠ Vérif. manuelle (P4) — saisir « Forcer rang »` while unresolved and `🔒 Rang forcé (P4)` once set.

**`simulateMatchResults`** (menu: "🧪 Simuler résultats de match") injects canned scores covering every code path (Normal/Mercy/Forfait/extra-innings/walk-off, plus deliberately tied scenarios at each tiebreaker priority level) onto whatever schedule is *already* generated in Résultats A/B — it does not touch Configuration or invent a fake schedule. It refuses to run (shows an alert) if Résultats A/B haven't been populated yet via "Générer les matchs". The canned `DATA` arrays are positional (1st game of pool 1, 2nd game of pool 1, ...) and intentionally agnostic to actual team names, so they keep working regardless of what real teams are in Configuration.
